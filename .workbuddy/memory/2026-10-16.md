## 关键约定（后续维护必读）
- `content/` 是文章唯一维护源；`src/` 与 `index.html` 是**生成物，必须提交**（Pages 直接
  以仓库根为站点根）。`sources/` 放 WAV。
- Markdown 兼容 `D:\user_project\git\DailyWork\english` 的既有格式：`# 标题` +
  `## Article / Words / Questions / Answers / Continues`；也支持 YAML front matter 与
  `## Q1` + `题型：单选/填空` + `可接受答案：` 扩展格式。答案支持紧凑字母串（`BAC`）、
  `Question5: …`、分块三种写法，可混用。
- 音频由外部工具 `009.ai_voice` 的 `publisher\eaudio.cmd` 生成（读 `## Article` 章节，
  输出与 md 同名的 WAV）；构建脚本**不做** TTS / 转码。
- 全站相对路径，禁止 `href="/…"`；`validate.py` 会检查。

## 修移动端 Continue 导航被撑高（本次）

用户：「桌面端没有问题，在移动端 Continues 下的标签显示太大了」。

### 根因（**flex-basis 在竖排里作用到高度**）
`.nav-link, .nav-disabled { flex: 1 1 200px }` 是共享规则，桌面端横向排时 200px 落在**宽度**上
（正好两个一行）；而 `@media (max-width: 640px)` 里 `.continue-nav { flex-direction: column }`
一翻转，**flex-basis 就变成每个标签的「高度」基准** ⇒ 上一页 / 下一页两张卡各被撑到 **200px 高**。

实测（playwright，`getBoundingClientRect()`）：

| 视口 | 修复前 | 修复后 |
|---|---|---|
| 390px 每张卡 | 366 × **200** | 366 × **52.6** |
| 390px `.continue-nav` 总高 | 472.6 | **177.9** |
| 900px（桌面） | 405 × 52.6 / 总高 115.3 | **完全不变** |

### 修法
只在移动端媒体查询里给三个子项加回自然高度，**不动共享规则**（桌面端依赖它均分宽度）：
```css
.continue-nav .nav-link,
.continue-nav .nav-disabled,
.continue-nav .nav-home { flex: 0 0 auto; }
```
CSS 里已加注释说明「竖排后 flex-basis 作用在高度上」，避免以后被当成冗余删掉。

### 同类隐患排查（已确认无第二处）
全站 `flex-direction: column` 只有 4 处：`.catalogue` / `.question-list` / `.options`（子项都是
`flex: none` 或无 px 基准）、以及移动端这一处 `.continue-nav`（本次修）。
其余 px 基准都在横向容器里：`.fill-input`（`1 1 220px`，父 `.fill-row` 是 row + wrap，移动端不翻转）、
`.player-body`（`1 1 auto`）、`.question-text`（`1 1 60%`）。**以后新增「竖排 + px 基准」组合必犯此错，
写 `flex-direction: column` 时先检查子项的 flex-basis 是不是长度值（px/200px），百分比与 auto 无此问题。**

- validate.py 不解析 CSS 内容（只查文件存在），加文本断言太脆 ⇒ 本次不加自动守卫，
  靠 CSS 注释 + 本条记忆锁。（要做真实布局回归需要浏览器，validate.py 限定只用标准库。）
- 只改 `assets/css/style.css`（+8 行），**生成物零字节变化**。

## 移动端 Continue 卡片「修复没生效」的真正原因：Pages 强缓存（本次）

用户再次反馈手机端 Continue 卡片过高（附截图，卡片仍是 ~200px 高）。**排查结论：上次的修复
已经部署且线上样式是对的，是手机拿了缓存的旧 CSS。**

### 证据链（这套查法以后照用）
1. `git rev-list --left-right --count origin/main...HEAD` → `0 0`：用户已 push。
2. `curl -s <线上 style.css>` → 17191 B，与本地 `assets/css/style.css` 字节数一致，
   且 `grep -c "flex: 0 0 auto"` = 1 ⇒ **线上带着修复**。
3. 对**线上真实页面**跑 playwright（`https://…/src/0002.…html`，宽度 320/360/390/412/480/560/640）：
   `dir=column`、每张卡 **52.6px**、且浏览器实际解析到的 CSS 里含修复 ⇒ 部署代码正确。
4. `curl -D -` 看响应头：`Last-Modified: 17:07:13`、**`Cache-Control: max-age=600`**；
   用户截图时间 **17:10** ⇒ 手机在部署前已缓存上一版，10 分钟窗口内继续复用旧文件。
   **这就是「明明改好了手机上却没变」的机制。**

### 采取的两项措施
1. **CSS / JS 的 URL 挂内容指纹**（根因处理）：
   `build.asset_version()`（sha256 前 8 位）+ `build.asset_url()` → `style.css?v=c4a9c9ef`；
   三个资源常量 `STYLE_CSS` / `MAIN_JS` / `PLAYER_JS`；首页与文章页模板统一走 `asset_url()`。
   只按内容算 ⇒ 构建仍字节级可复现（validate 第 6 节 PASS）。图标暂未加指纹（很少变动）。
   注：HTML 自身也有 10 分钟强缓存，所以手机上仍可能有 ≤10 分钟延迟，属 Pages 固有行为。
2. **布局修法从媒体查询挪回共享规则**（把坑从根上拆掉）：
   `.nav-link/.nav-disabled` 由 `flex: 1 1 200px` → **`flex: 1 1 0; min-width: 200px`**，
   并删除移动端那条 `flex: 0 0 auto` 补丁。原理：竖排时 basis 0 不再变高度，
   靠 flex item 默认 `min-height: auto` 回到内容高。
